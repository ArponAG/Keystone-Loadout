# 05 — UI

Four surfaces plus an admin page. Server Components read SQLite directly; only the
character lookup goes through a Route Handler.

## 1. Route table

| Route | Type | Reads | Purpose |
|---|---|---|---|
| `/` | Server | — | Surface picker + season banner |
| `/gear` | Server + Client form | `items`, `item_stats`, `item_sources` | Build Gear Finder |
| `/loot` | Server | `instances` | Instance grid, current rotation first |
| `/loot/[instanceId]` | Server | `encounters`, `items`, `item_sources` | Boss list + loot tables |
| `/character` | Client form → `/api/character` | `character_cache` | Raider.IO profile |
| `/news` | Server | `news` | Wowhead feed |
| `/sync` | Server | `sync_runs`, table counts | Admin: what is stale |
| `/api/character` | Route Handler | `character_cache` + Raider.IO | The one live passthrough |

Build state (`/gear`) lives in URL search params — `?armor=cloth&primary=intellect&order=haste,crit,mastery,vers`.
Shareable, bookmarkable, survives refresh, and lets the page stay a Server Component
with a small Client island for the form.

Parsing is **tolerant by design**: an unknown armor type or primary falls back to the
default, and a partial or duplicated `order` is completed from the default ordering
(`?order=vers` yields Versatility, Haste, Crit, Mastery). A hand-edited URL should
never produce a 500.

## 3. Surface 1 — Build Gear Finder (`/gear`)

**Flow:** pick armor type → primary → drag the four secondaries into order → results
render per slot, best fit first.

Results group by slot, and **within a slot, rank only against the same key level**
(see `04-scoring.md` §7.2). Slot order: head, neck, shoulder, back, chest, wrist,
hands, waist, legs, feet, finger, weapons, **trinket last**.

| State | Treatment |
|---|---|
| **Empty — no build chosen** | Form only, with a one-line explainer. No results skeleton, no fake rows. |
| **Empty — no items match** | "No `{armorType}` gear for this slot in the current rotation." Offer a link to `/loot` to browse everything unfiltered. |
| **Empty — DB never synced** | Full-page: "No loot data yet. Run `npm run sync:all`." Link to `/sync`. This is the honest state on a fresh clone. |
| **Partial data** | Amber banner naming the coverage. Still shows what exists. |
| **Stale data** | Amber banner. Threshold: 7 days. |
| **Error** | Errors are impossible here — this reads SQLite only. A DB read failure is a 500 boundary with "Database unavailable. Is `data/app.db` present?" |

`<DataFreshness>` renders the first applicable state, in this precedence:

1. **running** — a sync is in flight, so results are the *previous* sync's
2. **error** — last run failed; results are whatever survived
3. **incomplete** — "8 of 9 rotation dungeons have loot synced"
4. **partial** — last run finished with warnings
5. **stale** — older than 7 days

Coverage is **counted from `item_sources`, not read from the sync log**: a run that
reported `ok` weeks ago says nothing about a dungeon added to the rotation since. The
component renders nothing when data is fresh and complete, and owns its own spacing so
its absence leaves no gap.

This exists because ranked results look identical whether the underlying sync covered
all eight dungeons or six — the failure is silent by default, which is exactly the class
of problem this project keeps guarding against.

Always visible: the not-a-simulation banner; the trinket and weapon warnings pinned to
their sections; `NO_SECONDARIES` items shown with a "no secondaries" badge rather than 0%.

**Two decisions taken during Step 7:**

- **Scope toggle — "M+ rotation only" (default) vs "Everything synced".** Ranking is
  only valid within a tier, and rotation dungeons share one. Including raids mixes
  tiers, so it is opt-in and carries an inline caveat rather than being the default.
- **Reissued items are collapsed here, but not on `/loot`.** When an old dungeon
  re-enters the rotation Blizzard publishes a second item id under the same name: the
  legacy version has only a primary and Stamina, the reissue has the modern secondary
  template. 14 such pairs exist in the current data. The gear finder shows the
  better-scoring one with an `×2` marker, because an unscoreable twin is pure noise
  when the whole point is ranking. `/loot` still lists both — a loot directory that
  hides drops is lying, which is the same reason it shows mounts and recipes.

## 4. Surface 2 — Dungeon Loot Directory (`/loot`)

Grid of instances, current-rotation dungeons first and badged, then other dungeons,
then raids. Detail page lists bosses in `order_index` with a full loot table —
**including** the non-equippable mounts, recipes and housing decor, because a loot
directory that hides drops is lying. They render in a muted style, marked "not gear",
and are simply absent from `/gear`.

| State | Treatment |
|---|---|
| Empty — never synced | "No instances yet. Run `npm run sync:instances`." |
| Instance with no encounters | Card renders, disabled, "No boss data" |
| Encounter with no loot | Section header + "No loot recorded for this boss." Distinguishes "boss synced, drops empty" from "boss never synced". |
| Unknown instance id | `notFound()` → 404 page with link back to `/loot` |

## 5. Surface 3 — Character Lookup (`/character`)

**Primary input is a typeahead.** Type 2+ characters and a dropdown offers matching
characters with avatar, faction-coloured name, and `REGION · Realm · Class`. Picking one
fills region/realm/name and runs the lookup in a single click — which also removes the
realm-slug problem entirely for the common case.

- Backed by `/api/character/search`, which proxies Raider.IO's **internal** site search
  (`/api/search`), not their documented v1 API. It is what raider.io's own search box
  uses, but carries no stability guarantee — so **every failure degrades to an empty
  dropdown**, never an error, and the manual form below still works. Nothing depends
  on it, which is why `verify-assumptions` does not gate on it.
- 250 ms debounce, in-flight request aborted on each keystroke (so a slow response for
  `ni` cannot overwrite results for `niina`), 60-second server-side memo per term,
  8 results max. A personal tool should not hammer someone else's endpoint.
- Keyboard operable: ↑/↓ to move, Enter to pick, Escape to close.

The manual region/realm/name form is still present, collapsed behind
"Or enter realm and name manually", for characters the search does not surface.

Form: region (default `us`), realm slug, character name. Submits to `/api/character`.

Realm must be a **slug** (`moon-guard`, not `Moon Guard`). Normalise client-side:
lowercase, spaces and apostrophes to hyphens, and show the normalised value so a
failed lookup is diagnosable.

| State | Treatment |
|---|---|
| Idle | Form + one-line explainer |
| Loading | Inline spinner on the button; form stays interactive |
| 404 from Raider.IO | "Character not found. Check the realm slug and spelling — Raider.IO only knows characters it has crawled." Not cached. |
| Upstream 5xx, stale cache exists | Serve cached, amber note: "Raider.IO is unreachable — showing data from {time}." |
| Upstream 5xx, no cache | "Raider.IO is unreachable. Try again shortly." |
| Rate limited | "Too many lookups. Try again in a minute." |
| Success, cached | Subtle "cached {n} min ago" |

Render `gear.items` in slot order; ignore `azerite_powers` and `corruption`, which the
probe showed returning legacy junk. Show M+ score, equipped ilvl, spec, raid progression.

Each slot shows its enchant beneath the item name where one exists, from
`enchants_detail`. The redundant prefix is stripped — "Enchant Weapon - Berserker's
Rage" becomes "Berserker's Rage", since the row is already labelled MAINHAND.

We deliberately do **not** flag slots that are *missing* an enchant, tempting as it is
for a new-player audience. That needs a trustworthy set of enchantable slots, and
sampling live characters did not give one: `back` and `legs` came back unenchanted even
on well-geared raiders, so a naive "you're missing an enchant!" would fire on slots that
may not take one. A false warning is worse than no warning for the people this is for.

### 5.0 Saved characters

A rail of pinned characters above the search, each showing name, spec, realm, item
level and M+ score. Clicking one runs a full lookup.

Names are **class-coloured** (`classColor`, tokens in `globals.css`), which is what
every WoW UI does and what makes the rail scannable without labelling each card. Because
the colour already says the class, the second line spends its width on spec and realm —
the two things colour cannot say, and the pair that separates two alts of one class.

The active card is marked by a **filled background, not an accent outline**. An outline
competed with the class colours the cards are built around: a gold ring around a pink
Paladin name fights it, whereas fill sits behind the content. Cards are a fixed width so
the rail is a grid rather than a ragged row — names run from 2 to 12 characters.

Where Blizzard's avatar is missing (it can 404 on a freshly-renamed character) the card
falls back to the initial in class colour. An empty square reads as a broken image.

The pin control on the profile header is **icon only**, so state has to live in the icon:
hollow bookmark is an invitation, filled is a fact. It carries `aria-pressed` and an
`aria-label` naming the character, since a lone glyph names nothing to a screen reader.

Stored in **localStorage, not the database**. This started in SQLite, which was right
while the app ran on one machine for one person. Once it is served to several people
that inverts: a shared table means everyone sees one list and can delete each other's
entries. The data is personal to whoever is looking, so it belongs in their browser —
and that needs no accounts and no user column.

Reads are defensive: storage can be disabled, full, or hold entries from an older
build, and a malformed row costs that row rather than the whole list.

The stored ilvl/score are a **snapshot taken at save time**, so the rail renders
instantly with no upstream calls. They are a label, not a source of truth; clicking
refreshes them. Re-saving updates the snapshot but keeps the original `savedAt`, so the
list does not reshuffle every time you view someone.

### 5.0b Equipped gear audit

Two independent signals, deliberately not merged into one "good/bad" verdict:

- **Tier 1, relative.** Each slot against the character's own average. Colours the item
  level: amber 8+ below, green 8+ above. Needs no outside data and assumes nothing about
  what content they run. The average is computed over judged slots only, so a 331 weapon
  cannot drag the baseline up and make ordinary armour look weak.
- **Tier 2, absolute.** A `−N` chip showing how far a slot sits below the **Great Vault**
  reward for the key level this character actually clears. This is the "a low-ilvl player
  cannot get raid gear" part: the target is what *their* content awards.

**Trinkets and weapons are never judged**, in either tier — not coloured, not chipped,
excluded from the average. Their value is dominated by procs and weapon damage, which
item level does not capture; a lower-ilvl trinket routinely beats a higher one. Flagging
them would be confidently wrong exactly where the app is least able to judge, which is
the same reason `/gear` warns on those slots.

Two further honesty constraints:

- The target uses the **median** of best runs, not the maximum. One lucky high key does
  not mean a character reliably clears that level.
- It is labelled **vault**, not "drop", because that is what the data says. The game's
  reward table carries `WeeklyRewardLevel`; its `EndOfRunRewardLevel` column is 0 in
  every season, so end-of-run ilvls are simply not available and must not be implied.

With no reward curve in the database, Tier 2 disappears and Tier 1 still works.

### 5.0c What to get next

Concrete upgrades: which slot to fix, and which dungeon and boss drops it.

**Built for someone new to the game.** A new player does not know their stat priority
and should not have to before getting an answer, so the ordering that matters most is
the one needing no configuration:

1. **Which slot is furthest behind** — pure item level, no opinion required
2. **Which single dungeon covers the most slots** — the question actually being asked
   ("what should I run tonight"), and not answerable from a per-slot list without
   cross-referencing it in your head
3. **Which candidate suits them** — stat fit, offered as a refinement *below* the
   answer, in a collapsed panel, never as a prerequisite

Changing the stat priority re-ranks the candidates but **never reorders the slots** —
that is item level only. So the headline advice is identical whether or not the user
engages with it.

**Why this is well-posed at all:** Mythic+ normalises reward item level by key level,
so every rotation item arrives at the *same* item level for a given player. Choosing
between them is therefore purely slot need and stat fit, with none of the cross-tier
comparison problems that make `base_item_level` untrustworthy elsewhere. Raid loot is
excluded for exactly that reason.

**Resolved from data, not a hardcoded class map:**

- *Primary stat* — Blizzard's `playable-specialization` record, keyed by the spec id
  Raider.IO already returns. This is not fussiness: Midnight's Devourer Demon Hunter is
  an **Intellect** spec, so the obvious "Demon Hunter = Agility" map would be silently
  wrong and would recommend the wrong half of every loot table.
- *Armor type* — majority vote over the character's equipped armour, looked up in our
  own items table. Typically 3-4 of 8 pieces resolve, unanimously.

If either fails to resolve, that half of the filter is **skipped rather than guessed**,
which widens the results. An obviously-too-broad list is a better failure than an empty
one that looks like a bug.

Trinkets and weapons are excluded, consistent with the gear audit.

### 5.1 Mythic+ Progression

Stat tiles (score, timed, highest key, realm rank) over a best-runs table. The score
uses **Raider.IO's own tier colour** from `segments.all.color`, so it matches what their
site shows rather than inventing a second scale.

> **Deliberately not matching the reference exactly.** Raider.IO's site shows lifetime
> "2+ / 0+ Keystone Timed Runs" counters. Those are not in the public API — no
> `mythic_plus_run_counts` field exists, and invalid field names are silently ignored
> rather than erroring, so there is nothing to discover. We show timed runs *of best
> runs* (one per dungeon) and say so in a footnote rather than presenting a
> differently-derived number under the same label.

### 5.2 Talent Build

From `fields=talents`, which returns under the key `talentLoadout` (not `talents`).

- Laid out as three icon-only columns — **Class / Hero / Spec** — like the in-game
  tree. Names live in the tooltip rather than beside every icon.
- **Class and spec are not labelled in the payload.** Both carry `subTreeId: 0`; only
  hero talents differ. They are separated by `posX`: the game lays the two trees side by
  side, so columns sit ~600 apart *within* a tree and there is one large gap *between*
  them. The split is found by locating the widest gap per loadout rather than
  hardcoding a threshold, and is ignored unless that gap is at least twice the typical
  spacing. Verified across two classes (Warrior 31/28, Demon Hunter 30/30).
- `grantedNode: true` entries are dropped — automatic, not chosen.
- Nodes with no spell on any entry are dropped: the hero-tree *selector* is one of
  these, and would otherwise render as an "Unknown" chip.
- `maxRanks` is clamped to at least `rank`. Warrior's "Master of Warfare" spreads rank 4
  across three same-named entries with `maxRanks` 1/2/1, which would render "4/1".
- The import string is offered with a copy button — the single most useful thing here,
  since it pastes straight into the game.
- Payload is trimmed server-side: 31 KB of raw tree nodes down to ~6 KB.

### 5.2b Search, and the removal of the manual form

The typeahead is the **only** lookup control on the page. The "Or enter realm and
character name manually" form it used to sit above is gone: it duplicated what the
search does, and asked people to know that "Tarren Mill" is typed `tarren-mill`.

Two things had to move before it could go:

- **The loading indicator.** `loading` was surfaced *only* by that form's submit button,
  so deleting the form would have left the page inert after picking a suggestion or a
  pinned character. The search box now takes a `busy` prop and shows a spinner.
- **The fallback path.** A character the search cannot find is still reachable by URL —
  `/character?region=eu&realm=turalyon&name=Foo` — which the page already handled.

The dropdown also distinguishes *no matches* from *search is down*, because the endpoint
is undocumented and a silent empty list for an outage is a lie. Aborts are excluded from
the failure state: one fires on nearly every keystroke and means nothing went wrong.

Suggestions are class-coloured like the saved rail, so "this is a character" looks the
same everywhere in the app.

### 5.2b-ii `@theme static` is required, not stylistic

`globals.css` declares `@theme static`. Do not drop the keyword.

Tailwind v4 emits only the theme variables it can see used, by scanning source for
literal names. Two helpers here assemble a variable name at runtime — `classColor()`
returns `var(--color-class-${slug})` and `trackColor()` does the same for tracks — and a
name built from a template is invisible to that scan, so those tokens were omitted from
the stylesheet entirely and the `var()` resolved to nothing.

It failed silently and *selectively*, which is what makes it worth writing down:
`--color-track-hero` and `--color-track-myth` survived only because two test assertions
happened to contain them as literals, so Hero and Myth badges were coloured while
Champion and Veteran rendered fully transparent. The same trap was live for
`--color-class-evoker`. `static` emits everything unconditionally.

### 5.2c-ii Footer

Minimal by request: the Blizzard trademark line only. That line is **required by the
Game Data API terms** and is not a stylistic choice.

The "Data from Raidbots · Raider.IO · Wowhead · Blizzard" list was removed. Worth knowing
if this ever goes public: the Raidbots backlink was not decoration — it is their
published request in return for use of the static data files `scripts/sync-loot.ts`
reads. Leaving it out is defensible for a personal LAN instance and less so beyond one.

### 5.2c Borders

`--color-line` and `--color-line-strong` sit deliberately close to the surfaces they
divide. Borders here separate regions of a dense dark page and are never the only signal
for anything, so they can afford to be quiet; raising their contrast turns every card
into a boxed-in compartment and the page reads as a wireframe. These two tokens are the
global lever — change them and the whole app follows.

The one border that stays loud is the `:focus-visible` outline, which is an
accessibility affordance rather than decoration.

### 5.2d Upgrade track badges

Each equipped slot shows its upgrade track and rank — "Hero 1/6" — under the item level,
coloured along WoW's own quality ladder: Explorer grey, Adventurer white, Veteran green,
Champion blue, Hero purple, Myth gold. That progression is already in every player's
head, so the badge needs no legend. Each token is lifted off the canonical quality hex
toward the light end, because values chosen for coloured text on a light tooltip
(`#0070dd`, `#a335ee`) go muddy as a small tinted pill on `#16181f`.

The pill tint is 22%. At 14% only the brightest track read as a badge and the rest
looked like loose text, so one component appeared to be two designs down the column.

The badge exists because **item level alone is ambiguous**. On Thousandcuts-turalyon the
head and the chest are both 308, but one is Champion 6/6 (finished, replace it) and the
other Hero 2/6 (four upgrades still available). Track and rank are one badge rather than
two, since "Hero" without "1/6" hides the half that tells you what to do next.

**Where the data comes from.** Neither Raider.IO nor Blizzard states the track — both
return an item level and a bonus list, and the track is derived from the bonuses. This
was checked: Blizzard's `/equipment` endpoint has no upgrade field at all, and its
`name_description` is the *source* ("Mythic+"), not the track. Wowhead does the
derivation, so `npm run sync:upgrade-tracks` reads it back once into `upgrade_tracks`
and the request path is a pure local lookup.

Keyed by bonus id, not a formula. The ids do sit in runs of six with a stride of eight,
but **several blocks are live simultaneously** — 12793-12806 and 12817-12854 both
resolve — and the ranges move between patches, so arithmetic would silently mislabel
gear. Re-run the sync after a patch. An empty table yields no badges rather than wrong
ones, and the sync refuses to overwrite a good table with an empty result.

### 5.2e What to Get Next

Two controls: **per slot** (3/5/8) and **source** (All / Mythic+ / Raid, defaulting to
All). Both re-query the server rather than filtering client-side, so they live in
`CharacterLookup` beside the other lookup parameters. Both are validated in the route —
`perSlot` reaches a slice, and a hand-edited `perSlot=500` should degrade, not render.

**All ranks raid and dungeon drops in one list**, which is the point of it: a raid item
that fits better than every dungeon item comes first. Source selection happens in the SQL
filter, so `buildRecommendations` simply ranks whatever it is handed.

The honesty problem this creates is handled once, in the controls: the `+N ilvl` on each
slot header is the gap to the **Mythic+ vault reward**, exact for a key drop and only
indicative for a raid one, whose level depends on difficulty. We do not store that —
`base_item_level` reads 197/219 for raid and 59/108/219/250 for dungeons, none of which
resemble what players receive. So raid rows are labelled inline and the caveat is stated
once rather than repeated per row.

`byDungeon` excludes raids in every mode: it answers "which key should I run tonight",
and a raid boss is neither a key nor repeatable on demand.

**Best value runs** surfaces `byDungeon`, which the engine had been computing and the UI
had been discarding since it was written. "Which dungeon covers the most weak slots" is
the question a new player actually has, and it is not answerable from the per-slot list
without cross-referencing eleven dungeon names by hand. It counts M+ sources only — a
raid boss is not an answer to "what should I run tonight".

The per-row chips are gone. Spec, armour, primary, instance name and instance type each
used to carry a hand-tuned palette — the spec badge matched substrings like "prot" and
"fire" across five colour schemes, and eleven dungeons had assigned colours with a string
hash as fallback. That put two or three saturated colours in every row, competing with
the item-quality colour that actually carries meaning.

### 5.2f Mythic+, Talents, Raid progression

Lower-traffic sections, brought in line with the rest: no card outlines, fill instead of
borders, no gradient rules under the headings.

- **Mythic+** run rows show a bar for `clearTime / parTime`. Two timestamps require
  mental arithmetic to answer "how close was that to depleting", which is the thing you
  read the table for. Key badges are green when timed.
- **Talents** — the copy button now says what it copies ("Copy import string"). It is the
  most useful control in the section and it was labelled "Copy" with the explanation
  hidden in a `title`.
- **Raid progression** was quietly broken. It rendered Raider.IO's `summary` field, which
  is an **empty string until a boss dies**, so the value column was a column of blanks.
  It now counts from the per-difficulty numbers, which always say something, and shows a
  real empty state when nothing has been killed.

  Raider.IO also slugs an unnamed tier as `tier-mn-1`; title-casing produced "Tier Mn 1",
  which is not a raid anyone can search for. Those render as "Current tier" instead.

  Note when testing: every character returns all-zero raid progress right now, top
  raiders included — the tier is new. The populated branch was verified by stubbing the
  response, not by finding a character with kills.

### 5.3 Item tooltips

Wowhead's tooltip embed (`wow.zamimg.com/js/tooltips.js`) attaches to every
`wowhead.com/item=` link, which every item name in the app already is. Hovering gives
the real in-game tooltip: upgrade track, armor, full stats, durability, sell price,
"Dropped by".

Configured with `colorLinks/iconizeLinks/renameLinks: false` so it adds tooltips only
and leaves our own quality colouring and icons alone. Talent icons link to
`wowhead.com/spell=` so they get real talent tooltips for free.

**Equipped items must pass their bonus ids** (`wowheadItemUrl` in `lib/domain/icons.ts`).
A bare `item=` link makes Wowhead render an item at its *default* upgrade track, which
is the *maximum* one: Thousandcuts-turalyon's Hero 1/6 mainhand at 305 displayed as
Myth 6/6 at 334, overstating it by ~30 item levels on the one page whose whole job is
showing people what to upgrade. The fix is `?bonus=a:b:c` from Raider.IO's `bonuses`.

Note that `ilvl=` does **not** fix this — Wowhead derives the track from the bonus ids
and ignores a bare item level, so the obvious-looking fix is the wrong one. Verified
against `nether.wowhead.com/tooltip/item/251195`: bare and `ilvl`-only both render
"Myth 6/6" 334; with `bonus` it renders "Hero 1/6" 305. Covered by `icons.test.ts`.

`ench=` (single id, from `enchants`) and `gems=` (colon-separated item ids, from
`gems`) ride along the same way. The gear finder passes none of this — it lists items
nobody owns yet, so the generic item is the correct thing to show.

**Tooltips follow the cursor** (`components/TooltipPosition.tsx`). The embed's own
placement anchors to the link's right edge and bottom-aligns to its top, which is fine
for an inline link but lands hundreds of pixels away from a `block truncate` one — our
character-page item names span the whole grid cell. Rather than reshaping every link to
hug its text, a `mousemove` listener repositions the tooltip near the pointer, flipping
left and clamping up at the viewport edges. It is registered after the embed's own
handler so it wins on the same event, and does nothing while no tooltip is visible.

## 7. `/sync` (admin)

One row per source: last run, status (`ok` / `partial` / `error` / `running`), record
count, the terminal command, and a **Run sync** button. Row colour by staleness —
green <24 h, amber <7 d, red beyond. A `running` row older than 30 minutes is flagged
as a probable crashed run.

> **Decision changed.** This page was originally specified read-only, on the reasoning
> that a ~530-request loot sync should not be one click away in a browser. It now has
> run buttons by explicit request. The reasoning was sound, so the protection moved
> into the mechanism rather than being dropped:

- **Hard allowlist.** `lib/sync/registry.ts` is the only source of runnable scripts.
  The source name from the request selects a row; it is never interpolated into a
  command. The child is spawned via `process.execPath` with a fixed script path and
  **no shell**.
- **Concurrency lock in shared state.** `withSyncRun` refuses to start when a
  `running` row exists for that source, so the lock covers the terminal as well as the
  browser — not just the button. A locked run exits non-zero with a readable message.
- **The row is created by the Server Action, not the child.** The action inserts the
  `running` row and passes its id to the script as `--run-id=N`, which the script
  adopts instead of opening its own. This makes the state visible the instant the click
  returns, and closes the double-click race where two clicks could both pass the lock
  check before either child had booted.
- **Two-step confirm for expensive runs.** The loot button arms on first click and
  fires on second. Deliberately *not* `window.confirm` — it blocks the thread and
  browsers can suppress it, which silently turns the guard into a no-op.
- **Detached child.** The sync outlives the request; navigating away or closing the tab
  does not kill it. `sync_runs` is the single source of truth for progress.
- **Polling only while something runs.** An idle `/sync` makes no background requests.

Failing to spawn marks the row `error` immediately rather than leaving it to the
30-minute reaper.

## 9. Cross-cutting

- **No loading skeletons for DB reads.** SQLite reads are sub-millisecond; a skeleton
  would be theatre. Skeletons only on `/character`, the one genuinely async surface.
- **Empty states name the command that fixes them.** This is a personal tool; the user
  and the operator are the same person.
- **Every empty state distinguishes "no data" from "no results".** "Nothing synced yet"
  and "nothing matches your build" need different fixes and must never share wording.
